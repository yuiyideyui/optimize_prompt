# ComfyUI 漫画转动漫自动化插件 — 第一阶段开发需求

## 一、项目定位

开发一个 **ComfyUI 自定义节点插件**，作为完整漫画转动漫自动化系统的基础。

插件使用 ComfyUI 工作流组织各个步骤，以 Gemini 作为漫画理解模型，并建立持久化知识库与 RAG 检索能力，为未来的角色参考图生成、场景生成、分镜生成和视频生成提供基础。

### 完整项目的未来目标

1. 导入整章漫画图片。
2. 使用 Gemini 按顺序分析漫画页面，理解人物、场景、剧情、对话和动作。
3. 通过上下文和 RAG 保持跨页、跨章节的连续性。
4. 建立角色、角色外观版本、场景、剧情事件等持久化知识库。
5. 后续使用 Qwen-Image-Edit 2511 生成角色参考图、三视图和场景参考图。
6. 自动检查生成的图片是否符合原漫画设定。
7. 后续使用 MiniMax H3 等视频模型生成动漫片段。
8. 检查角色身份、外观、动作、镜头和剧情连续性。

当前实现已覆盖漫画理解、数据持久化、基础 RAG、跨章节连续性记忆和 ComfyUI 节点交互；本仓库同时提供一个基于 ComfyUI 原生节点组合的 Qwen Image Edit 自定义节点。完整的视频生成、视频续写和自动质量检查仍不属于本模块。

## 二、ComfyUI 插件开发要求

### 2.1 插件形式

必须开发为可安装到 ComfyUI `custom_nodes` 目录下的独立自定义节点插件。

不要将项目实现为需要在命令行中单独运行的漫画处理程序，也不要要求用户离开 ComfyUI 才能完成主要操作。

插件应支持：

- ComfyUI 工作流节点调用。
- ComfyUI 的图片输入与输出数据类型。
- 多张漫画图片的批量输入。
- 节点之间传递章节、页面、角色和场景等数据。
- 持久化数据库和本地文件管理。
- 工作流保存、重新加载与再次执行。
- 单页失败后的重新处理。
- 将处理结果传给后续自定义节点。
- 与其他 ComfyUI 图片生成节点连接。

### 2.2 ComfyUI 节点标准

遵循 ComfyUI 自定义节点的标准开发方式，正确实现节点映射、输入定义、输出定义和执行函数。

至少正确使用：

- `INPUT_TYPES`
- `RETURN_TYPES`
- `RETURN_NAMES`
- `FUNCTION`
- `CATEGORY`
- `NODE_CLASS_MAPPINGS`
- `NODE_DISPLAY_NAME_MAPPINGS`

节点输出类型必须有明确的数据结构。对于复杂数据，可以使用插件定义的自定义数据类型，但必须保证不同节点之间能够稳定传递和复用。

优先使用 ComfyUI 已有的数据类型；只有在确实需要传递章节、角色、场景等结构化数据时，才定义专用类型。

不要为了显示信息而将所有结构化数据转换成字符串。

### 2.3 ComfyUI 兼容性

- 不修改 ComfyUI 核心文件。
- 不依赖修改 ComfyUI 源码才能运行。
- 尽量避免修改全局 Python 环境。
- 避免安装与 ComfyUI 已有依赖冲突的库。
- 不要在插件导入时执行 Gemini 请求。
- 不要在插件导入时扫描整个漫画目录或初始化大型模型。
- 不要在节点执行时阻塞无关的 ComfyUI 功能。
- 处理长任务时应提供合理的日志和错误信息。
- 根据实际环境设计兼容方案，不要假设所有 ComfyUI 用户都使用相同的 Python 版本。

如果需要前端扩展，应作为独立的可选功能；第一阶段优先使用 ComfyUI 原生节点界面完成工作流操作。

## 三、整体节点工作流

第一阶段建议使用以下节点组织流程：

```text
[漫画目录输入 / 图片批量输入]
              |
              v
[漫画章节导入节点]
              |
              v
[漫画页面排序与校验节点]
              |
              v
[历史知识检索节点] <---- [持久化知识库]
              |
              v
[Gemini 漫画页面分析节点]
              |
              v
[页面结果保存节点]
              |
              v
[角色与场景实体整理节点]
              |
              v
[章节总结节点]
              |
              v
[知识库更新节点]
              |
              v
[结果输出 / 后续工作流]
```

上述为逻辑流程，实际实现时可以合并职责高度相关的节点，但必须保持模块清晰。

不要将所有功能写进一个超大的节点，也不要为了节点数量而将每个简单函数都拆成独立节点。

必须保证节点可以在工作流中按需组合。

### 数据传递原则

- 图片通过 ComfyUI 的 `IMAGE` 类型传递。
- 页面列表使用明确的结构化数据类型。
- 章节上下文使用明确的结构化数据类型。
- 角色和场景资料使用明确的结构化数据类型。
- Gemini 分析结果使用结构化数据类型。
- 数据库中的持久化记录使用稳定 ID 引用。
- 文件路径只用于定位持久化文件，不应替代结构化数据本身。

不要直接把所有信息打包成难以验证的任意字典并在节点之间随意传递。应定义统一的数据模型和 Schema。

## 四、建议实现的自定义节点

### 节点 1：漫画章节导入

建议名称：`Comic Chapter Loader`

输入：

- 漫画图片目录，或其他合适的图片输入方式。
- 项目 ID。
- 章节 ID。
- 文件排序规则。
- 是否检查重复图片。

输出：

- 页面列表。
- 项目 ID。
- 章节 ID。
- 导入统计信息。

功能：

1. 扫描指定目录中的漫画图片。
2. 支持 PNG、JPG、JPEG 和 WEBP。
3. 按文件名或指定规则排序。
4. 计算图片哈希并识别重复文件。
5. 记录图片尺寸、来源路径和文件信息。
6. 为每张页面分配稳定 ID。
7. 保留原始漫画图片。
8. 记录导入结果和错误。

同时考虑直接从 ComfyUI 的 `IMAGE` 输入接收图片的方式，避免所有用户都必须使用目录输入。

如果 ComfyUI 的图片输入无法携带原始文件名，应为导入后的页面分配稳定序号，并允许用户指定页面顺序。

### 节点 2：漫画页面排序与校验

建议名称：`Comic Page Validator`

输入：

- 页面列表。
- 排序配置。
- 重复图片处理策略。

输出：

- 校验后的页面列表。
- 校验报告。

功能：

- 检查页面顺序。
- 检查重复图片。
- 检查无效文件和缺失文件。
- 检查页面 ID 是否重复。
- 标记需要人工确认的顺序问题。

不得在无法判断页面顺序时静默采用错误顺序。

### 节点 3：RAG 历史知识检索

建议名称：`Comic Knowledge Retriever`

输入：

- 项目 ID。
- 当前章节 ID。
- 当前页面内容或页面描述。
- 可选的角色、场景或剧情查询。
- 返回结果数量。
- 检索策略。

输出：

- 相关角色资料。
- 相关角色外观版本。
- 相关场景资料。
- 相关剧情事件。
- 相关历史页面引用。
- 检索来源和置信信息。

功能：

1. 优先执行结构化查询。
2. 支持基础文本检索。
3. 为后续向量检索预留接口。
4. 根据当前页面检索相关历史记录。
5. 返回可追溯的来源信息。
6. 不将文本相似度直接当作角色身份匹配结论。

当当前页面尚未分析时，可以先利用章节上下文和已知条件检索候选信息；完成初步分析后，也可以再执行一次针对角色或场景的检索。

### 节点 4：Gemini 漫画页面分析

建议名称：`Gemini Comic Page Analyzer`

输入：

- 当前漫画页面。
- 项目 ID。
- 章节 ID。
- 页面 ID。
- 前序页面摘要。
- RAG 检索结果。
- 已知角色与场景资料。
- Gemini 模型配置。
- 分析提示词版本。

输出：

- 页面分析结果。
- 更新后的上下文摘要。
- 分析状态。
- 错误或警告信息。

功能：

分析漫画中的：

- 页面主要内容。
- 分格及阅读顺序。
- 角色身份候选。
- 角色外观与服装。
- 表情、动作和情绪。
- 场景及环境特征。
- 对话、旁白和拟声词。
- 角色关系。
- 剧情事件。
- 与前后页面的连续性。
- 明确事实、推测和未知信息。

使用 Gemini 支持的结构化输出能力，并对响应执行严格的本地 Schema 校验。

如果页面包含多个分格，应尽可能分析各分格的内容与顺序。无法可靠识别分格时，应保留整页分析，并标记不确定性。

不要要求 Gemini 对所有字段强行给出答案。

### 节点 5：页面结果持久化

建议名称：`Comic Page Result Saver`

输入：

- 页面分析结果。
- 项目 ID。
- 章节 ID。
- 页面 ID。
- 保存策略。

输出：

- 已保存记录的 ID。
- 保存路径。
- 保存状态。

功能：

- 保存页面 JSON。
- 更新 SQLite 中的页面分析记录。
- 记录模型名称、提示词版本和分析时间。
- 记录成功、失败和待确认状态。
- 支持重复执行。
- 支持单页重新分析。
- 支持数据版本管理。

如果重新分析同一页面，应明确采用更新现有记录、保留历史版本或生成新版本的规则，不得静默产生重复数据。

### 节点 6：角色与场景实体整理

建议名称：`Comic Entity Resolver`

输入：

- 页面分析结果。
- 已有角色和场景候选。
- 当前知识库。
- 匹配阈值与策略。

输出：

- 已确认角色。
- 新角色候选。
- 待确认角色匹配。
- 场景匹配结果。
- 新外观版本。
- 处理报告。

功能：

#### 角色身份

判断新记录是否属于已知角色，依据包括：

- 面部特征。
- 发型与发色。
- 稳定外观特征。
- 人物关系。
- 剧情背景。
- 历史页面视觉证据。

#### 角色外观版本

同一个角色可以拥有多个外观版本，例如校服、便服、战斗服或特定剧情阶段的状态。

角色身份与外观版本必须分开存储。

不能仅因服装变化创建新角色，也不能因为名字相同就自动合并身份。

#### 场景身份

区分地点本身与该地点的不同视觉状态，例如白天、夜晚、天气变化和不同镜头视角。

存在歧义时，保留待确认结果，不得直接覆盖历史资料。

### 节点 7：章节总结

建议名称：`Comic Chapter Summarizer`

输入：

- 章节 ID。
- 页面分析结果列表。
- 已确认角色与场景。
- 历史上下文。

输出：

- 章节总结。
- 主要剧情事件列表。
- 角色清单。
- 场景清单。
- 未解决问题列表。

功能：

- 汇总整章剧情。
- 整理主要事件的发生顺序。
- 总结角色行为与关系变化。
- 整理场景出现顺序。
- 记录结尾状态与未解决问题。
- 记录信息来源页面。
- 将明确事实与推测分开。

章节总结应能从已保存的页面分析结果重新生成，不需要再次分析全部漫画图片。

### 节点 8：知识库更新

建议名称：`Comic Knowledge Base Updater`

输入：

- 页面分析结果。
- 实体整理结果。
- 章节总结。
- 更新策略。

输出：

- 知识库更新报告。
- 新增实体列表。
- 更新实体列表。
- 待确认记录列表。

功能：

- 更新角色身份记录。
- 更新角色外观版本。
- 更新地点和场景状态。
- 更新剧情事件。
- 更新角色关系。
- 更新 RAG 索引。
- 维护来源与证据关系。
- 处理历史记录与新记录之间的冲突。

知识库更新必须具备幂等性：相同的结果重复执行时，不应无条件产生重复实体。

### 节点 9：知识库查询

建议名称：`Comic Knowledge Query`

输入：

- 项目 ID。
- 查询类型。
- 角色 ID、场景 ID 或自然语言查询。
- 章节过滤条件。

输出：

- 查询结果。
- 相关来源记录。
- 相关图片路径。
- 对应实体 ID。

用于调试知识库，也为后续工作流提供可复用的角色、场景和剧情资料。

## 五、上下文管理与 RAG

必须明确区分三种机制。

### 5.1 Gemini 短期上下文

用于同一章节相邻页面之间的连续理解。

内容包括：

- 前序页面剧情摘要。
- 当前主要角色。
- 当前场景。
- 近期事件。
- 尚未解决的问题。

不要把所有历史页面的完整分析永久堆积在上下文中。

### 5.2 SQLite 持久化知识库

作为角色身份、场景身份、外观版本、剧情事件及处理状态的权威数据源。

Gemini 的临时上下文不能替代数据库。

### 5.3 RAG 历史检索

用于从历史章节和大量页面中找出与当前页面有关的资料。

初期使用 SQLite 结构化查询和基础文本检索，后续可以接入向量数据库。

RAG 检索结果必须包含实体 ID 和来源信息，便于进一步查询原始漫画页面。

## 六、数据模型与存储

建议使用 SQLite 作为持久化数据库，并保存可读 JSON。

至少应设计以下数据实体：

- `projects`
- `chapters`
- `pages`
- `panels`
- `characters`
- `character_aliases`
- `character_appearances`
- `character_appearance_evidence`
- `locations`
- `location_states`
- `story_events`
- `character_relationships`
- `entity_matches`
- `analysis_runs`
- `chapter_summaries`
- `dialogues`
- `story_event_participants`
- `rag_index_records`

关键要求：

- 使用稳定 ID。
- 使用适当的外键和索引。
- 记录创建与更新时间。
- 页面、分格、角色、场景和剧情事件必须能够相互关联。
- 每个重要事实都应尽可能关联来源页面或分格。
- 支持单页重分析与数据更新。
- RAG 索引可重建。
- 数据库损坏或索引丢失时，不能导致原始漫画和 JSON 结果一起丢失。

推荐的数据目录：

```text
ComfyUI/
└── custom_nodes/

        ├── __init__.py
        ├── nodes/
        │   ├── comic_loader.py

        │   ├── chapter_summarizer.py
        │   ├── knowledge_updater.py
        │   ├── rag_index_rebuilder.py
        │   └── __init__.py
        ├── core/
        │   ├── models.py
        │   ├── schemas.py
        │   ├── database.py
        │   ├── context_manager.py
        │   ├── entity_matching.py
```

可以调整目录，但应将 ComfyUI 节点、业务逻辑、数据库、RAG 和模型 API 客户端分离。

持久化数据使用可配置的数据根目录，并提供合理的默认值。若默认放在插件目录下，必须通过 `.gitignore` 排除数据库、漫画原图和运行日志，避免提交到代码仓库。

## 七、API 与运行要求

### Gemini API

支持配置：

- API Base URL。
- API Key。
- 模型名称。
- 请求超时时间。
- 最大重试次数。
- 请求并发或速率限制。
- 提示词版本。

必须支持兼容的 API 中转服务。

API Key 应从环境变量或本地配置读取，并避免在日志、节点输出和工作流文件中泄露。

### 长任务

漫画章节可能包含大量页面，因此需要：

- 可恢复的处理状态。
- 单页失败重试。
- 明确的错误日志。
- 合理的 API 限流。
- 可配置的批量处理策略。
- 单页重分析。
- 防止重复写入。
- 避免不必要的重复 API 调用。

ComfyUI 的节点执行应遵循其运行机制，不要擅自创建会与 ComfyUI 执行器冲突的后台任务。

如果需要异步请求、任务队列或进度显示，应先根据当前 ComfyUI 版本选择兼容方案，不要假设普通 Python 后台线程就能自动提供可靠的节点进度和取消能力。

## 八、第一阶段验收标准

### A. ComfyUI 安装与加载

- 插件能正确放入 `custom_nodes` 目录。
- ComfyUI 启动时可以加载插件。
- 所有节点能正常显示。
- 节点输入和输出类型正确。
- 不需要修改 ComfyUI 核心文件。

### B. 漫画导入

- 支持导入多张漫画图片。
- 排序正确。
- 可以检查重复文件。
- 页面 ID 稳定。
- 原始图片不被修改。

### C. Gemini 分析

- 可以通过工作流调用 Gemini。
- 分析结果符合结构化 Schema。
- 能识别角色、场景、对话和剧情。
- 输出能够保存为 JSON 和数据库记录。
- API 失败不会破坏已有数据。

### D. 跨页连续性

- 后续页面能够使用前序页面摘要。
- 能检索已知角色和场景。
- 服装变化不会自动导致角色身份重复。
- 有歧义的匹配能够保留待确认状态。

### E. RAG

- 可以查询历史角色。
- 可以查询历史场景。
- 可以查询剧情事件。
- 查询结果可以追溯到原始页面。
- 索引可以重建。

### F. 断点续跑

- 中断后可以继续执行。
- 单页可以单独重试。
- 单页可以重新分析。

## 第一阶段 A—F 实现与使用

当前插件实现覆盖阶段 A—F：ComfyUI 节点注册、漫画页面导入、Gemini 分析、跨页上下文、保守的实体候选匹配、可重建的 SQLite 文本检索、章节总结及幂等知识库更新。向量检索、完整自动图片生成、视频生成和真实 ComfyUI 环境验收仍未实现。

### 当前版本新增能力

- `Comic Page Context Builder` 会按章节顺序读取前序页面，并在固定 `context_budget` 内组织近期页面、当前状态和开放剧情线索。
- 页面分析结果新增 `state_changes`、`new_open_threads` 和 `resolved_threads` 的持久化更新；状态记录带有确定性、置信度和来源页面。
- `ComicDatabase.rebuild_story_memory(project_id)` 可从每页最新分析重建派生状态与剧情线索，适合重新分析或修复数据库后的恢复操作。
- `Gemini Comic Page Analyzer` 会先按项目、章节和页面哈希查询缓存，命中时直接复用最近的结构化分析结果。
- `QwenImageEditCustomNode` 注册在 `QwenImageEdit` 分类，输入一张必选参考图和最多两张可选参考图，输出编辑后的 `IMAGE`。

Qwen 节点依赖当前 ComfyUI 提供的 `UNETLoader`、`CLIPLoader(type="qwen_image")`、`TextEncodeQwenImageEditPlus`、`FluxKontextImageScale`、`KSampler` 等节点；对应模型文件和 ComfyUI 版本兼容性需要在实际环境中确认。

### 安装

将本目录作为独立插件放入 ComfyUI 的 `custom_nodes` 目录，例如：

```text
ComfyUI/custom_nodes/ComfyUI-Comic2Anime/
```

如果当前 ComfyUI 环境没有 Pillow，再使用 ComfyUI 正在使用的 Python 安装 `requirements.txt` 中的依赖。随后设置 Gemini API Key 环境变量并重启 ComfyUI：

```powershell
$env:GEMINI_API_KEY = "your-api-key"
```

不要将 API Key 写入工作流、节点参数或插件配置文件。插件使用 `GEMINI_API_KEY` 环境变量，不会把 Key 放入节点输出或日志。

### 工作流

1. 添加 `Comic Chapter Loader`，填写项目和章节 ID。
2. 选择以下一种或同时使用两种输入：
   - 在 `directory` 填写图片目录；支持 PNG、JPG、JPEG、WEBP，按文件名或自然数字顺序排列。
   - 连接 ComfyUI `IMAGE` 批次；节点会将批次图片副本写入插件数据目录。
3. 选择重复图片策略。`skip` 忽略重复内容，`keep` 保留并记录，`error` 遇到重复时停止。
4. 将 `pages` 输出连接到 `Gemini Comic Page Analyzer`。`page_index` 从 1 开始，每次执行分析所选的一页；可选提供前序页面摘要，并可配置模型、兼容 API Base URL、超时和最多 5 次重试。
5. 为跨页理解，可将 `Comic Page Context Builder` 的 `previous_summary` 输出接到分析节点的同名输入，并将 `retrieved_knowledge` 接到分析节点对应输入。该节点只取当前页之前有限数量的页面摘要，并从项目知识库提供带来源页引用的候选资料。
6. 将分析结果连接至 `Comic Entity Resolver`。输出包含已确认匹配、新实体候选和待人工确认匹配；`review_threshold` 和 `auto_confirm_threshold` 控制保守匹配。姓名/别名相同只能生成待确认候选，不足以自动合并；服装、动作、表情不作为稳定身份特征。节点不会用模型生成的名称猜测替代来源证据。可将如下 JSON 填入可选 `review_decisions` 输入，按 `source_index` 明确确认或拆分候选：`{"characters":[{"source_index":0,"decision":"confirm","matched_entity_id":"已有角色 ID"}]}`；`decision` 也可为 `separate`。确认后将解析结果重新连接到知识库更新节点执行。
7. 将原始分析和实体整理结果连接到 `Comic Knowledge Base Updater`，写入角色、角色外观及证据、地点状态、剧情事件、角色关系和文本索引。重新分析后再次运行更新节点会替换该页面的当前证据，避免旧事件残留；数据库中的分析运行和 JSON 历史版本仍保留。
8. 使用 `Comic Knowledge Retriever` 按项目、实体类型、章节、实体 ID 或文本查询角色、地点、剧情事件、分格、对话与角色关系。检索结果包含实体 ID、页面 ID、分格索引和可用时的原图路径。若索引丢失或损坏，执行 `Comic Knowledge Index Rebuilder` 从结构化 SQLite 记录重建。
9. 使用 `Comic Chapter Summarizer` 从 SQLite 中每页最新的已保存分析重建章节总结，不调用 Gemini；它输出按页总结、剧情事件、角色/场景清单、未分析页及未解决问题。节点可单独重建；也可以将知识库更新报告接入它的可选输入，以确保先更新知识库再生成总结。

建议连接顺序：

```text
Comic Chapter Loader
    ├──> Comic Page Context Builder ── previous_summary / retrieved_knowledge ──┐
    └──> Gemini Comic Page Analyzer <───────────────────────────────────────────┘
                  └──> Comic Entity Resolver
                            └──> Comic Knowledge Base Updater
                                               └── update_report ──> Comic Chapter Summarizer
Comic Knowledge Retriever <── 已更新的 SQLite / RAG 索引
```

页面分析节点一次处理 `page_index` 指定的单页；批量章节处理可通过逐页执行并保留已完成的分析记录来断点续跑。重试同一页不需要重调其他已完成页面。章节总结从已存分析重建，若新增或重分析页面，应在更新知识库后重新运行总结节点。ComfyUI 会根据节点输入变化决定是否重新执行上游；本插件未实现后台队列或中断后自动调度。

### D/E/F 数据与匹配说明

- SQLite 保存角色身份与 `character_appearances` 外观版本、`character_appearance_evidence` 来源证据分离的数据；服装变化只形成新的页面外观证据，不创建新的角色身份。
- `entity_matches.status = pending_review` 持久化有歧义的候选关系；解析器不会仅按名字/别名或文本相似度直接宣告身份相同。自动确认同时要求精确名称/别名候选与高置信、可区分的稳定外观描述证据；只有文字相似但名称不同仍保留待确认。
- 地点身份和 `location_states` 视觉状态分开。剧情事件、角色关系、分格与对话都关联来源页面；角色参与者可关联到实体 ID。
- RAG 初期使用 SQLite 持久化文本索引和本地词项匹配，不依赖向量数据库。可通过 `rebuild_project_index` 从结构化知识记录重建索引，原始页面证据以稳定 page ID 追溯。
- `Comic Knowledge Base Updater` 对实体、外观、来源证据、关系和事件使用稳定 ID/唯一约束；同页重跑会更新当前记录，不会无条件增加重复实体。历史 Gemini 分析运行仍保留，可用于重新构建总结。
- 章节总结的剧情与页面事实来自已保存的 Gemini 结构化分析；角色/地点清单和待确认项来自已更新的知识库，并携带来源页 ID。重建总结不产生新的模型判断。

默认持久化目录为自定义节点根目录下的 `comic2anime_data`（例如 `ComfyUI/custom_nodes/optimize_prompt/comic2anime_data`）。该运行时数据目录已加入 Git 忽略规则。可通过 `COMIC2ANIME_DATA_DIR` 指定其他目录。数据库为 `comic2anime.sqlite3`，原始目录图片不会被修改；IMAGE 输入会另存为插件管理的 PNG 副本。
